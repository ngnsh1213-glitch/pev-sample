# PEV 견본 — 계획(Plan) · 실행(Execute) · 검증(Verify)

AI에게 코드를 맡길 때 "알아서 잘 해 줘" 대신 **계획서 → 지시서 → 보고서**로 일하는 방식의 최소 견본입니다.
계획하는 역할, 만드는 역할, 검사하는 역할을 나눕니다. 지휘와 판정은 엔지니어가 합니다.

| 역할 | 하는 일 | 규칙 파일 |
|---|---|---|
| 계획 · 검토 | 계획서와 지시서를 쓰고, 보고서를 검토한다. 코드는 직접 고치지 않는다 | `CLAUDE.md` |
| 실행 | 지시서 범위 안에서만 코드를 고치고, 보고서를 쓴다 | `AGENTS.md` |
| 지휘 · 판정 | 계획을 승인하고, 지시서를 넘기고, 결과가 맞는지 최종 판단한다 | 엔지니어 |

## 1. 두 단계로 시작합니다

| 단계 | 언제 | 도구 | 비용(대략) |
|---|---|---|---|
| **1단계 — AI 하나** | 처음. 이 방식에 익숙해질 때까지 | Claude Code **또는** Codex 중 하나(CLI) | 가장 싼 요금제 1개, 월 3만 원대 |
| **2단계 — 두 회사 AI** | 익숙해져 본격적으로 코딩하다가 뜻대로 진행이 안 될 때, 다음 단계로 가고 싶을 때 | 계획·검토 = Claude Code, 실행 = Codex | 요금제 2개, 월 6만 원대 |

- 처음부터 비싼 요금제나 여러 개를 결제하지 마십시오. **1단계에서 양식과 흐름에 먼저 익숙해지는 것**이 목적입니다.
- 2단계로 가면 만든 AI와 검사하는 AI가 **다른 회사**가 됩니다. 같은 AI는 자기 실수를 잘 못 보는데, 다른 회사 AI는 다른 곳을 봅니다. 덤으로 사용량도 두 곳으로 나뉩니다.

### 1단계 — AI 하나로 역할 나누기

도구는 하나지만 **대화를 나눠** 역할을 나눕니다.

- 계획 대화: "`CLAUDE.md`를 읽고 계획 담당으로 일해"
- 실행 대화(**새 대화**): "너는 실행 담당이다. `AGENTS.md`를 읽고 `pev/HANDOFF.md`를 실행해"
- 검토 대화(**새 대화**): "`CLAUDE.md`를 읽고 `pev/REPORT.md`와 변경 내용을 검토해"

계획을 쓴 대화에서 바로 실행까지 시키지 않는 것이 핵심입니다. 앞 대화의 생각을 이어받으면 검토가 느슨해집니다.

## 2. 준비 (10분)

1. 쓸 CLI를 설치합니다. 설치 방법은 바뀔 수 있으니 각 공식 안내를 따르십시오.
   - Claude Code: `npm install -g @anthropic-ai/claude-code`
   - Codex: `npm install -g @openai/codex`
2. 작업할 폴더(가능하면 git 리포)에 이 견본의 `CLAUDE.md`·`AGENTS.md`를 복사합니다.
3. 두 파일 맨 아래 **「이 프로젝트의 값」** 칸을 채웁니다(빌드·실행 명령, 건드리면 안 되는 폴더 등).
4. 폴더에 `pev/`를 만들고 `templates/`의 양식 세 개를 참고용으로 둡니다.

## 3. 한 바퀴 돌리기 (2단계 기준 — 1단계는 「Codex」 자리를 새 대화로 바꿔 읽으십시오)

```
 ① 엔지니어 → Claude   "이 일을 계획해 줘: <하고 싶은 일>"
                        → pev/PLAN.md (계획서)
 ② 엔지니어            계획서를 읽고 승인 또는 수정 지시
 ③ 엔지니어 → Claude   "승인. 지시서 써 줘"
                        → pev/HANDOFF.md (지시서)
 ④ 엔지니어 → Codex    "pev/HANDOFF.md를 읽고 실행해"
                        → 코드 변경 + pev/REPORT.md (보고서)
 ⑤ 엔지니어 → Claude   "pev/REPORT.md와 변경 내용을 검토해"
                        → 통과 / 되돌림 판정 근거
 ⑥ 엔지니어            최종 판정. 통과면 커밋, 아니면 ③으로
```

- 지시서를 실행 쪽에 **넘기는 것은 엔지니어가 직접** 합니다. AI끼리 알아서 이어 달리게 두지 않습니다.
- 끝난 한 바퀴의 `PLAN`·`HANDOFF`·`REPORT`는 `pev/archive/<날짜>_<주제>/`로 옮겨 기록을 남깁니다.
  무엇을 왜 바꿨는지 남아 있어야 같은 자리를 맴돌지 않습니다.

`example/`에 한 바퀴 예시(배관 자재 목록에서 관경별 길이 합계 내기)가 계획서 → 지시서 → 보고서 → 검토 순으로 있습니다.
검토(`REVIEW.md`)에서 실행 담당이 지시서에 없던 동작을 넣은 것을 잡아내는 장면을 보십시오.

## 4. 처음 할 때 지킬 것 세 가지

1. **계획서 없이 코드를 고치게 하지 않는다.** "이거 해 줘"를 바로 던지면 AI도 무엇이 완료인지 모릅니다.
2. **"다 했습니다"를 믿지 않는다.** 보고서의 검증 결과를 확인하고, 가능하면 직접 한 번 돌려 봅니다.
3. **만든 쪽과 검토하는 쪽을 나눈다.** 1단계는 대화를, 2단계는 회사를 나눕니다.

## 5. 이 견본에 없는 것

이 견본은 시작용 최소판입니다. 실제 업무에서 수백 바퀴를 돌리며 붙인 다음 것들은 담지 않았습니다.

- 지시서 ↔ 보고서 짝 맞춤·형식 검사 등 **자동 검증 도구**
- 세 번째 AI를 검토자로 더하는 **교차 검토 운영 방식**
- 반복 실패를 막는 규칙, 기록이 쌓였을 때의 정리 방식
- 팀 단위 도입 절차
